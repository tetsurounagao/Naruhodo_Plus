# Naruhodo+ 要件定義書（v4）

学習蓄積・クイズ生成アプリ「Naruhodo+」の要件定義書。

## 1. 目的

業務やチュートリアル中に生じた疑問・学びを「なるほどで終わらせず」蓄積し、そこから復習クイズを自動生成して知識の定着を図る。将来的には社内の他の新人にも配布できる形を目指す。

## 2. 基本方針

- **完全個人完結**：業務由来の情報を扱うため、他ユーザーとの共有機能は持たない
- **AIエージェント非依存**：Claude・Codexなど、その時々で使うAIを問わず同じ蓄積先にアクセスできるようにする
- **追加コストなし運用**：クイズ生成などのAI処理は、個人のAIサブスクの範囲（チャットでの会話）で完結させ、別途API従量課金を発生させない
- **配布を見据える**：他の新人が使う場合は、GitHub等で雛形を配布し、各自が自分のDB・自分のAIエージェントを接続して使う「セルフホスト型」にする

## 3. 全体アーキテクチャ

```
[Claude / Codex 等のAIエージェント]
        │  MCPツール呼び出し（stdio接続）
        ▼
[MCPサーバー（ローカルPC稼働、TypeScript/Node.js）]
        │  読み書き（Supabase service role key使用）
        ▼
[Supabase DB（個人用・無料枠、クラウド）]
        ▲  読み書き（サーバー側のみ）
        │
[Next.js APIルート（Vercelにデプロイ）]
        ▲  ログイン済みセッション経由でのみアクセス
        │
[ブラウザ（Web画面、PC・スマホ）]
```

- **MCPサーバー**：普段の作業中（PC）に、学びの記録・クイズ生成の橋渡しをする窓口。生成AIロジック自体は持たず、CRUD（保存・取得）に徹する。Codex CLI・Claude Code/Desktopともにstdio方式のローカルMCPサーバーに対応しているため、この構成で問題ない（2026年時点で確認済み）
- **Web画面**：クイズに解答する・進捗を見る・タグ別集計を見る、という「参照・実行」系を担当
- **役割分担の理由**：クイズ"生成"はチャット上でAIに頼むことで追加コストを発生させず、クイズ"解答"はどこからでも（スマホ含め）行えるようにするため

## 4. 認証・データアクセス方式

Vercelのデプロイ先URLは公開されるため、Web画面には認証を必須とする。学習コストは設計者（開発者）側のみに発生し、利用者（ログインするだけ）には影響しない。

- **ログイン機能**：Supabase Auth（メールアドレス＋パスワード）を利用する。パスワードのハッシュ化やセッション管理など、セキュリティの根幹部分は実績のある仕組みに任せる
- **データアクセス経路**：ブラウザはSupabaseに直接接続せず、必ず**自前のNext.js APIルートを経由**する。Supabaseへの強い権限（service role key）はサーバー側の環境変数にのみ置き、ブラウザには一切渡さない
- **API側の処理フロー**：リクエスト受信 → ログインセッションの検証 → Supabaseへの読み書き → レスポンス返却
- **MCPサーバー側の認証**：ローカルPCで動作する信頼された処理として扱い、service role keyを直接環境変数として保持する（RLSの設定は不要）
- この構成により、Supabaseの行単位アクセス制御（RLS）を自分で設計・学習する必要がなくなる

## 5. データベース設計（Supabase / PostgreSQL）

### テーブル構成

| テーブル | 役割 |
|---|---|
| `knowledge_items` | 学び本体（質問・回答・文脈・情報源） |
| `tags` | タグのマスタ |
| `knowledge_item_tags` | 学びとタグの中間テーブル（多対多） |
| `quizzes` | 生成されたクイズ本体 |
| `quiz_tags` | クイズとタグの中間テーブル（多対多） |
| `quiz_attempts` | 解答履歴（正誤・解答日時） |

### スキーマ概要（DDLたたき台）

```sql
create table knowledge_items (
  id uuid primary key default gen_random_uuid(),
  question text not null,
  answer text not null,
  context text,           -- どのタスク・チュートリアル由来か
  source text,            -- 自分で調べた／AIに聞いた 等
  created_at timestamptz default now()
);

create table tags (
  id uuid primary key default gen_random_uuid(),
  name text unique not null   -- 正規化済み(小文字・空白除去)の名前
);

create table knowledge_item_tags (
  knowledge_item_id uuid references knowledge_items(id) on delete cascade,
  tag_id uuid references tags(id) on delete cascade,
  primary key (knowledge_item_id, tag_id)
);

create table quizzes (
  id uuid primary key default gen_random_uuid(),
  question text not null,
  choices jsonb not null,        -- 選択肢配列。下記「選択肢のデータ構造」参照
  correct_answer text not null,  -- 正解の選択肢id（例:"a"）を格納
  explanation text,
  source_knowledge_id uuid references knowledge_items(id),
  created_by text,               -- 生成したAI名(claude/codex等、任意メモ)
  created_at timestamptz default now()
);

create table quiz_tags (
  quiz_id uuid references quizzes(id) on delete cascade,
  tag_id uuid references tags(id) on delete cascade,
  primary key (quiz_id, tag_id)
);

create table quiz_attempts (
  id uuid primary key default gen_random_uuid(),
  quiz_id uuid references quizzes(id) on delete cascade,
  user_answer text not null,     -- 選択した選択肢id
  is_correct boolean not null,
  answered_at timestamptz default now()
);
```

### 選択肢のデータ構造（画像問題への拡張を見据えた汎用設計）

`choices`カラムには、以下のような構造のJSON配列を格納する。`type`によってテキスト問題・画像問題の両方に対応できるようにする。

```json
{
  "choices": [
    { "id": "a", "type": "text", "content": "useState" },
    { "id": "b", "type": "text", "content": "useEffect" },
    { "id": "c", "type": "image", "content": "https://.../diagram.png" }
  ],
  "correct_answer": "a"
}
```

- `id`：選択肢の識別子（正誤判定・UIでの選択管理に使用）
- `type`：`text`または`image`
- `content`：`type`が`text`なら表示文字列、`image`なら画像URL
- 正誤判定は常に`correct_answer`と選んだ選択肢の`id`を比較するだけなので、選択肢の中身がテキストでも画像でもロジックを変更する必要がない

### タグの正規化ポリシー

- タグ名はMCPサーバー側のコードで機械的に正規化（小文字化・前後空白除去・簡単な表記ゆれ変換）してから既存タグと照合する
- AIには「タグ名の文字列を渡すだけ」でよく、類似判定などの追加思考はさせない（コスト・安定性の両面で有利）
- 完全な同義語の統合（例：「React」と「フロントエンド」）は自動化せず、Web画面上で手動整理する運用とする

## 6. クイズ生成フロー

1. Web画面に「未出題のナレッジ一覧」を表示
2. 該当項目の「クイズ化を依頼」ボタンを押すと、AIに投げるプロンプト文がクリップボードにコピーされる
3. 普段使っているチャット（Claude/Codexなど）にペーストして送信
4. AIがMCPツール（`list_knowledge`等）で元データを取得し、選択式クイズを生成
5. `save_quiz`ツールで結果をDBに保存
6. Web画面をリロードすると新しいクイズが一覧に反映される

- **解答形式は選択式のみ**（まずはこれで開始。正誤判定はWeb画面側で完結し追加コスト無し。将来的に記述式も検討）
- 解答・正誤記録はブラウザ→Next.js API→Supabaseの経路で書き込む（MCP経由不要）
- **同じ学びから複数回クイズを生成した場合**：重複を気にせずそのまま蓄積する（苦手タグ判定の母数が増えるだけなので許容する）

## 7. MCPツール一覧（たたき台）

| ツール名 | 引数（例） | 役割 |
|---|---|---|
| `add_knowledge` | question, answer, context?, source?, tags[] | 学びを保存する。保存前に機密情報の抽象化・簡易パターンチェックを行う |
| `list_knowledge` | tags?, unquizzed_only?, limit? | クイズ生成などのためにナレッジを条件抽出する |
| `save_quiz` | question, choices, correct_answer, explanation, tags[], source_knowledge_id | 生成したクイズを保存する |
| `get_tag_stats`（任意） | tag? | タグ別の正答率・件数をチャット上で確認できるようにする |

## 8. 機密情報対策（3段構え）

業務中の学びを扱う以上、機密情報の混入リスクをゼロにはできないため、以下の多層防御で運用する。

1. **抽象化ルール**：`add_knowledge`実行時、AIが固有名詞・社内特有の文脈を取り除き、技術的な概念のみを一般化して保存する（ツールの指示文にルールを明記）
2. **機械的ガード**：MCPサーバー側で、保存直前にAPIキーらしき文字列・社内ドメイン・メールアドレス等を正規表現でチェックし、該当時は保存を止めてアラートを出す（AIの追加コストなし）
3. **保存前プレビュー**：保存内容の要約を事前に表示するかどうかは、**ユーザーが設定でON/OFFを切り替えられる**ようにする（初期は確認あり、慣れたらOFFにする運用も可能）

## 9. 苦手タグ検出ロジック

- 正答率ベースで判定する
- 各タグごとに`quiz_attempts`を集計し、一定回数以上（暫定：3回以上）解答済みで、正答率が閾値未満（暫定：60%未満）の場合を「要復習タグ」とする
- 計算はSQLの集計のみで完結し、追加のAI呼び出しは発生しない
- Web画面ではタグ一覧・クイズ一覧に警告表示、円グラフでタグ別の出題比率も可視化する

## 10. 配布方針（将来）

- GitHubに雛形リポジトリを作り、他の新人はそれをダウンロード
- 各自でSupabaseプロジェクトを作成し、接続情報を設定
- 各自でMCPサーバーを自分のPCで起動し、使いたいAIエージェントに接続
- Web画面はVercelに各自デプロイ（無料枠）
- セットアップ画面（Web画面内）で接続テストやMCP設定用の文字列コピーができるようにし、非エンジニアでも迷わず導入できるようにする

## 11. 技術スタック（確定）

- MCPサーバー：TypeScript / Node.js（stdio接続）
- Web画面：TypeScript / Next.js（APIルート経由でSupabaseにアクセス）
- 認証：Supabase Auth（メールアドレス＋パスワード）
- DB：Supabase（PostgreSQL、無料枠）
- ホスティング：Vercel（無料枠）

## 13. 複数AIエージェントを使い分ける際の設計指針

### 接続設定は一度きり

各エージェント（Claude、Codex等）のMCP設定に、それぞれ一度サーバーの起動コマンドを登録しておけばよい。日々の「今日はどっちを使うか」の切り替えに、都度の再設定は不要。

### 振る舞いルールは一元管理する

「メモしてと言われたら保存する」「機密情報を抽象化する」「タグを使い回す」といった振る舞いのルールは、**MCPツールの説明文（サーバー側コード）に一元的に記述する**。MCPの仕組み上、この説明文は接続してきたどのAIにも自動的に渡されるため、これが唯一の情報源になる。CLAUDE.mdやAGENTS.mdのようなエージェント個別の指示ファイルに同じルールを重複して書かない（更新漏れによる挙動のズレを防ぐため）。

### スラッシュコマンドには機能の実行可否を依存させない

MCPの「プロンプト」機能をスラッシュコマンドとして扱う仕組みは、Claude Codeでは対応済みだが、Codex CLIは2026年時点で未対応（対応待ちの要望が上がっている段階）。そのため、確実な発火手段としては**自然文でのトリガー（「メモして」等）をツールの説明文に明記する方式を主軸**にする。スラッシュコマンドは「対応しているクライアントで使える追加の利便機能」という位置づけに留める。

### 実行許可は二層構造で考える

1. **クライアント側の許可設定**：Claude Code・Codex CLIなどが標準で持つ「このツールを実行していいか」という確認ダイアログ。設定で「常に許可」に変更できるが、クライアントによっては挙動が完全に安定しない場合がある（既知の不具合報告あり）
2. **アプリ独自の保存前プレビュー**：`add_knowledge`を「下書きを返すだけの呼び出し」と「実際に保存する確定呼び出し（例：`confirm_knowledge`）」の2段階に分けることで、モデルの気の利かせ方に依存せず、プレビュー機能を確実に動作させる設計にする（プレビュー設定がOFFのときはこの2段階をスキップし直接保存する）

### created_byフィールドの活用

クイズや学びを保存したエージェント名（claude/codex等）を`created_by`に実際に記録しておくと、後からエージェントごとの生成品質・タグの付け方の違いを検証できる。

## 14. 将来のローカルAI（Ollama等）拡張方針

### 導入目的の整理

クイズ生成自体はチャット経由でAIに頼む方式のため、そもそもサブスクの従量課金は発生していない。よって「メインのクイズ生成をローカルAIに置き換えてコストを下げる」動機は薄く、精度面でも見劣りする可能性が高いため対象外とする。一方、以下の2用途は無料・オフラインで完結できる価値があり、将来的な拡張候補とする。

- **タグの意味的重複検出**：文字列の完全一致では拾えない類義タグ（例：「React」と「フロントエンド」）を、埋め込みモデル等でグルーピングする
- **機密情報チェックの二重チェック**：正規表現による機械的ガードに加え、ローカルAIによる二次チェックを行う（機密情報の可能性がある文章を外部AIに送らずに済む点でも安全）

### 実装方針：1コードベース＋設定でON/OFF

PCの容量・スペックの都合を考慮し、アプリを2バージョン別々に維持するのではなく、**1つのコードベースで、ローカルAI利用を設定ファイル（環境変数等）でON/OFFできる形**にする。Ollamaをインストールしない場合は、今まで通りの軽量な構成（文字列正規化＋正規表現チェックのみ）で動作する。

### 設計上の備え（v1実装時点で意識する点）

タグの一致判定・機密情報チェックのロジックを、それぞれ「差し替え可能な1つの処理単位（関数）」としてまとめておく。呼び出し側のコードを変えずに、中身だけ「ローカルAIに問い合わせる版」に後から差し替えられるようにしておくことで、将来の拡張時に全体を作り直す必要がなくなる。
